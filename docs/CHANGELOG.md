## Recently shipped (2026-08-18, the deferred half — sync registry, popover contract, last prompt)

- **The three follow-ups the audit filed rather than attempted, plus the two findings it left partial.** Full gate suite green (`yarn lint`, `yarn lint:tokens`, `yarn typecheck`, `yarn test` — 1841, `yarn build`, `docker build`, `yarn test:e2e` — 113 chromium).
- **`sync-manager`'s twenty-arm switch is a registry now, and the guard matters more than the dedup.** Seventeen arms repeated the same twelve lines: hand the action to a store, mirror it into one Dexie table. The duplication was not the danger — the silence was. Pair a model with the wrong table and it still type-checks (both buckets are `object[]`) and still applies to the right MobX store; rows just never reach the offline cache. Forget a model entirely and *nothing* fails, which is how `Organization` went unhandled for months. `sync-manager.models.test.ts` now reads both sides from source and fails if a model the server emits is neither cached, bespoke, nor in the exported `UNCACHED_MODELS` — and separately asserts each model is paired with the table its name derives from. That second assertion is the one `yarn typecheck` provably cannot make; it was verified by mis-pairing `Team` with `users` and watching only the test go red.
- **`useRetryableFetch` stopped throwing away the error.** It exposed `errorMessage: string | null`, which discarded exactly what callers needed: `gqlQuery` throws a `GqlError` carrying `extensions.code`, so two pages had to re-catch inside their own fetcher to recover a code the hook was already holding — each inventing its own sentinel to smuggle it back out. The hook returns `cause` unchanged; `settings/audit-log` loses an `AuditOutcome` union and `settings/webhooks` loses a `forbidden` field, both replaced by `isPermissionError(cause)` at the render site.
- **A backlog entry proposed a refactor, and reading the call sites is what rejected it.** §4.6 said to rebuild `SimpleSelect` on `SelectPopover`. Its five call sites need a trigger `id` to pair with a `<label htmlFor>`, an `aria-label` for rows whose visible label is a plain `<span>`, and a non-selectable caption row above the options — three new props on the shared primitive, existing for one shape, plus a trigger restyle nothing in CI can verify without a visual-regression suite. What actually hurt was the duplicated *behaviour*, and the two copies had already drifted: the `SimpleSelect` one shipped without Escape and without focus restore, which together made an open panel a keyboard trap. That contract is now `usePopoverPanel`; the components stay two components. Write down why a proposal was rejected, or it comes back.
- **The last `window.prompt` was last because it was the hard one.** The editor's link prompt runs against a live ProseMirror selection: a native prompt blocks synchronously and never touches it, so `extendMarkRange('link')` was guaranteed to act on what the user highlighted. A dialog takes focus into the browser's top layer, and a selection restored only by `.focus()` is one you are *hoping* survived — get it wrong and the link silently lands on the wrong text. The fix is not to trust focus: capture `from`/`to` when the dialog opens and replay them with `setTextSelection`.
- **`as never` on the TipTap commands stays, and now says why.** The documented fix is a `declare module '@tiptap/core'` augmentation. It cannot work here: the package ships a rollup-bundled `index.d.ts` that declares the interface as `Commands$1` and re-exports it as `Commands`, so an external augmentation declares a *new* interface rather than merging into the one `RawCommands` is built from. Tried it, watched `addCommands()` still fail, and left the evidence in the comment — an "obvious" cleanup that has already been attempted is worth a paragraph.
## Recently shipped (2026-08-18, E2E — nine disabled tests re-enabled, and the accumulation bug that disabled them)

- **Nine e2e tests had been switched off as CI flakes. They were not flaky; they were the canaries for a data-accumulation bug, and it reproduces on demand.** Four cross-tab tests in `sync.spec.ts` (skipped whenever `CI` was set), four triage action tests and one offline test (`.fixme`). All nine pass. The chromium suite goes from 113 passing / 8 skipped to **118 passing / 3 skipped**, and the three that remain are honest — an initiative-updates feature that does not exist, and two property pickers the current seed does not render.
- **The mechanism is a threshold, not a race, which is exactly why it read as scheduling noise.** `GroupSection` virtualizes a group past **20 rows**; beyond that a newly created row is not in the DOM at all, so `getByText(title)` on a just-created issue fails with "element(s) not found". Specs create issues and mostly do not remove them, so the list grows within a run and across runs. One clean chromium run ends at ~9 rows in the largest group; a two-browser run ends at 18; a third run against the same database is over.
- **The repro nails it.** Run the suite against a database two previous runs have dirtied and **exactly ten tests fail — all four of `sync.spec.ts`, all four of `offline.spec.ts`, `issue-crud`'s create, and `issue-detail`'s inline edit** — every one of them on "element(s) not found" for a title it had just created. That set is very nearly the set that was disabled. Reseed and the same ten pass. The disabling notes had already written down the decisive clue without recognising it: results moved *"on adjacent runs whose only diff was a `.fixme` line"* — a diff that changes nothing except how many issues run before the affected test.
- **So the suite now cleans up after itself instead of the constraint being documented.** A `cleanup` teardown project archives every issue the run created, leaving the seeded six. Archiving rather than deleting is deliberate: the list queries filter on `archivedAt IS NULL`, so it is precisely the state that decides whether the threshold is crossed, and no history is destroyed. Three consecutive runs on **one** seed are now green and the database returns to exactly the seeded six after each; before this, run 2 on a shared seed was 111 passed / 10 failed.
- **That teardown shipped broken twice, the same way both times, and that is the lesson.** First it queried `issues` with no `filter.teamId`, which the resolver rejects — the unchecked `errors[]` read as "0 issues to clean up". Fixed, it then quietly skipped every snoozed issue, because `Query.issues` hides those by default and triage's snooze flow is exactly what leaves them behind (`includeSnoozed: true`). Both versions logged a confident "archived N" and left rows behind. So the teardown no longer asserts on its own effort — it re-queries afterwards and asserts **nothing non-seeded remains**, which is the only check that fails when cleanup stops working. Regressed to prove it: disable the archive loop and the teardown goes red.
- **The triage half was a separate and cruder problem: the row locator was a Tailwind utility list.** `div.flex.items-center.gap-3.border-b`. One `cn()` edit and it matches nothing — which surfaces as the "row still visible" symptom the notes describe, because the only assertion that can then fail is the one asserting the row *should* be there. It is now `data-testid="triage-row"`, the one line of product code this change touches.
- **The suite is roughly twice as fast, because it no longer logs in 130 times.** Nearly every spec replayed the whole magic-link flow in `beforeEach` — three navigations and two mutations, ~3s, for a test body that often ran in 100ms. A `setup` project signs both seeded accounts in once and parks the cookies; specs declare `test.use({ storageState: ADMIN_STATE })` and call `openWorkspace(page)`, a single `goto('/')` through the workspace redirect. Same wall time as before at **half the workers** — 5.7 min at one worker versus 6.0 min at two, and one worker is what CI actually uses.
- **Sharing one session across ~110 tests is safe here for two specific reasons, both worth naming before someone "improves" them.** Access tokens live 24h, so nothing in a 6-minute run triggers the refresh-token rotation that could revoke a family out from under a sibling test; and `issueTokenPair` starts a *new* family per login rather than revoking existing ones, so the specs that still log in for real cannot knock the shared sessions over. `loginAs` is kept for exactly those — the specs that are *about* signing in.
- **The obvious speed fix — build once, serve with `next start` — is unavailable, and the blocker is a security gate doing its job.** The dev server recompiles each route on first hit, 15–25s of the run. But the `TEST_AUTH_CODE` bypass is gated on `NODE_ENV !== 'production'` *because* Turbopack inlines that value at compile time, so a production build statically eliminates the bypass and nothing can authenticate. Building with `NODE_ENV=test` to dodge that would also swap React's production build for its development one — i.e. stop testing what ships.
- **Two more latent flakes surfaced once the suite ran often enough to see them.** `auth.spec`'s invalid-code case asserted `getByRole('alert')`, which also matches Next's route announcer (`<div role="alert" id="__next-route-announcer__">`, holding "Verify — Bilinear") — two matches is a strict-mode violation, but only when the announcer still has its text as the rejection lands, which is why it passed far more often than it deserved to. Now scoped to the form.
- **The other one is a real, if one-frame, product race, and the test now presses through it.** `issue-detail`'s Shift+S failed once in nine full runs with no error and no change. The bell renders as soon as the subscription query resolves, but `useHotkeys` registers its listener from a `useEffect` keyed on `subscribed` — so for one commit after the bell paints, the registered handler still closes over `subscribed === null` and returns early. Playwright can beat that effect; a person would just press again, so the test does too (the press moved inside the `expect.poll`). Worth knowing generally: **every `useHotkeys` binding has a window between paint and registration**, and any test that presses a shortcut the instant its target appears can land in it.
- **Mixed-role specs are split by role rather than by test.** `permissions` and `platform-admin` interleaved admin and member logins; `storageState` is per-block, so they are grouped into `as a non-admin member` / `as a platform admin` describes. `gqlInPage` still needs `openWorkspace` first — the fetch runs in the page, so the page must be on the app origin for cookies to attach.

Full gate suite green on the pinned Node 24 (`yarn lint`, `yarn lint:tokens`, `yarn typecheck`, `yarn test` — 1795, `yarn build`), plus `yarn test:e2e` — 120 chromium, and 237 across chromium + firefox.

## Recently shipped (2026-08-18, frontend audit — rollout gaps and the fixes that needed fixing)

- **A full-codebase frontend review, then two rounds of remediation on its own output.** 17 audit findings closed, plus 15 more found by a multi-agent review of the remediation itself. Full gate suite green (`yarn lint`, `yarn lint:tokens`, `yarn typecheck`, `yarn test` — 1795, `yarn build`, `docker build`, `yarn test:e2e` — 113 chromium). The audit report is [`REVIEW.md`](../REVIEW.md).
- **E2E is what caught the one regression no other gate saw, and it nearly did not run.** The audit and both remediation passes were done with E2E unavailable (no Docker daemon, so no Postgres or Redis); it was brought up at the end. The suite came back 104/9, and the nine split three ways: six fail identically at the base commit, two were dev-server compile timeouts under 36-way parallelism, and **one was real** — the webhooks page's `if (error) return <InlineRetry/>` replaced the whole page, so a non-admin hitting FORBIDDEN saw a bare error line instead of the page. Build, typecheck, lint and 1795 unit tests were all green on that. The lesson is the split itself: a red suite is not evidence until you have run the base commit too.
- **The six pre-existing failures were a stale-locator bug, and they had been red on `main` since 2026-08-05.** All six find picker rows with `getByRole('button')`, but those rows became `<button role="option">` when §4.2's listbox pattern shipped — and an explicit role *replaces* the implicit one, so the query cannot match. Fixed to `getByRole('option')`, which keeps each test's intent and additionally asserts the role. Adding a role to a component silently invalidates every `getByRole` that assumed the old one.
- **The codebase was in good shape, and the drift was all one shape: a good pattern adopted where it was invented and then not rolled out.** `useRetryableFetch`+`InlineRetry` had 18 component adopters and 15 page files still hand-rolling the fetch state machine, five of which rendered a failed load as a dead-end message where the rule requires a retry. `useDocumentTitle` had reached 6 of 26 workspace pages — the exact defect its own doc comment says it was written to fix. `runPoolStoreTests` had factored out the *test* for the pool-store shape while the implementation stayed copied twelve times. None of these were disagreements about the convention; they were unfinished rollouts.
- **The one real bug the audit found was hiding behind two plausible-looking dependency arrays.** `team/[key]/analytics` memoised on `issueStore.findByTeamId` — a prototype method whose identity never changes — so every chart froze at the data present when the page mounted. Three `eslint-disable` comments sat directly on it, which is how it stayed camouflaged: **this repo lints with Biome and has no ESLint**, so all seven such comments in the tree suppressed nothing while reading as "reviewed and waived". A suppression comment for a linter you do not run is worse than no comment.
- **The `pool.size` convention has an exception, and getting it wrong is a regression the first pass shipped.** `findByTeamId` is a method — keying a memo on it never invalidates, so `pool.size` is strictly better. `userStore.all` is a MobX **computed** — its identity already changes on an in-place row update, so re-keying it onto `pool.size` made a rename invisible until someone joined or left the org. Same file, same commit, opposite correct answers. The rule is about what the dependency *is*, not where it lives.
- **Two fixes had to be un-fixed.** `use-visible-columns` moved a `localStorage` write out of a state updater to preempt a StrictMode double-invoke — which introduced a real lost update (two calls in one React batch both build from the pre-batch value), then took a ref and an effect to climb back to parity. The original was always both batch-safe and mount-safe. It is reverted, with a comment recording why, so it is not "fixed" a third time.
- **Advertising an ARIA pattern without implementing it is worse than advertising nothing.** `SimpleSelect` was given `aria-haspopup="listbox"`+`aria-expanded` while its panel rendered plain buttons — a screen reader is told "listbox" and handed unroled buttons. Implementing it properly then shipped a **keyboard trap**: focus moved into the panel with no `closeOnEscape` and no focus restore, and inside a `ModalDialog` Escape closed the whole modal instead of the dropdown, violating the one-Escape-one-surface contract. The lesson is in the ordering — the half-measure, the correct-looking fix, and the trap were three separate commits.
- **`window.prompt` is now banned alongside `window.confirm`, for a concrete reason.** The platform-admin impersonation picker printed a numbered list of organizations and asked an operator to *type an index*: one mistyped digit impersonated into the wrong tenant, with no confirmation. It is now a dialog of labelled buttons. `PromptDialog` in `shared/` covers the two suspend-reason prompts. No new copy was written — every dialog reuses the key the prompt already passed to `window.prompt`.
- **Two staleness bugs of identical shape came from holding pagination outside the fetch.** Both audit pages kept `nextCursor` in their own state and wrote it from inside the fetcher, outside `useRetryableFetch`'s monotonic request-id guard: a late response had its rows discarded but its cursor kept, so the next "Load more" paged from the previous filter. Anything that must be discarded together with the data has to travel *in* the data.
- **"Not found" and "not allowed" are answers, not failures.** Neither is retryable, so neither trips `error` — offering a Retry that can never succeed is worse than offering none. `tenants/[id]` lets a missing tenant resolve to `null`; `settings/audit-log` returns a `forbidden` variant. `useRetryableFetch` gained `errorMessage` for the admin console, where the server's own text is the diagnostic rather than noise.
- **Six pages deliberately still hand-roll their fetch, and that is not drift.** They fetch-then-*seed-a-form*, spreading one response across many `useState` fields; routing them through the hook means calling `setX(...)` from inside the fetcher, which is the one place that must stay pure. Recorded in §80.6 so the next sweep does not "finish the job" and make it worse.
- **The DRY extractions were kept narrow on purpose.** `POPOVER_ITEM_CLASS` is a constant, not a component, because `SelectPopover`'s roving-focus query walks the real buttons each call site renders. `chart-geometry.ts` shares the burndown/burnup *frame* — scales, path serialisation, ticks — but not a chart component, which would have needed a switch per difference. `applyPoolSyncAction` is a free function rather than a base class so every store keeps its own `action`-annotated method and MobX annotations are untouched; 17 methods across 15 stores delegate, `IssueStore` deliberately does not, and `applyInitiativeProjectSyncAction` omits `'A'` because the server never emits one for that entity.
- **The test net around that helper was thinner than it looked.** One guard protecting 17 call sites had a single non-vacuous test: the null-data case asserted through `findById`, which is `get(id) ?? null`, so a row overwritten with `null` still read back as `null` and the test could not fail. Every new assertion added here was regressed to prove it can fail — removing the null guard turns 7 red, the verb check 5, the chart tick spacing 4.

## Recently shipped (2026-08-05, cycle-list progress + touch targets)

- **The cycle list and the cycle detail view disagreed about the same cycle's progress.** §80.7's "derived values are computed GraphQL fields" fix landed on `cycle-detail-view` and missed `cycle-list-view`, which kept counting client-side over `issueStore` with `completedAt != null` as the done-rule. Three separate ways that diverges, and only the first is the one usually cited: a guest's local pool holds only the issues they created or are assigned, so one owned issue in a 50-issue cycle rendered **100%**; the server counts a state type of `completed` **or** `canceled` as done and a canceled issue never receives a `completedAt`, so the client **undercounted every cycle containing one — for members, not just guests**; and the pool only holds what has synced. Fixed by reading `Cycle.progress`/`scope` like the projects list does.
- **That fix needed no server work, which is worth knowing for the next list.** `cycles(teamId:)` is an unpaginated list field and `Cycle.progress`/`scope` resolve through the per-request `cycleProgress` DataLoader, so selecting them across the whole list coalesces into a single `getProgressBatch` — no plural resolver, no N+1, no SDL change. A row renders no bar until the query lands rather than a placeholder 0%, and one `InlineRetry` covers the page; a per-row retry would be N copies of one failure.
- **The 44px mobile touch target was opt-in by copy-paste, at 51 sites across 33 files.** Hand-typing a WCAG 2.5.8 affordance means every new icon button silently ships without it, which is a slow leak rather than a one-time mistake. Now two constants — and the split between them is load-bearing, not cosmetic: `TOUCH_TARGET` sets a width *floor* because the reaction bar's trigger renders "🙂 React" and the editor toolbar renders `B`/`I`/`U` glyphs, while `TOUCH_TARGET_SQUARE` pins an exact 44×44 for controls wrapping a fixed-size icon. Collapsing the two would clip the first group.
- **They are strings rather than a `Button` variant, deliberately.** Zero of the 51 sites render `<Button>` — they are raw `<button>`/`<Link>` elements — and the six `SelectPopover` triggers structurally *cannot* take a component, because the popover renders its own trigger and exposes only a `triggerClassName` string. A CVA size would have helped none of them without a much larger, visually riskier migration onto `<Button asChild>`.
- **Five destructive settings actions still used `window.confirm`.** Archive an automation rule, revoke a SCIM token, remove the SAML config, disconnect Slack, disconnect GitHub — all now `ConfirmDialog`, with the gate moved out of the mutation into a `pendingAction` state (a union where a page has two distinct actions). No new dictionary keys were needed: every message was already a `t()` call, and each dialog's title reuses the button label already rendered on that page.
- **`estimate-picker` was the picker the combobox a11y pass missed** (REVIEW_BACKLOG §4.2). Its options had no `role="option"`/`aria-selected` while its three siblings did. It is a listbox *only* in the branch that renders a scale — with no estimation scale the panel is a free-form number field, and `role="listbox"` over a form field is exactly the mismatch `SelectPopover`'s `listbox` contract warns about, so the prop is bound to `scale != null` rather than set outright. It also picked up the `e.stopPropagation()` its four siblings already had; without it a pick bubbles to the clickable row behind the picker.
- **A backlog entry was corrected rather than closed.** §4.4 named the module-scope `mkdirSync` in the upload route as the cause of the Turbopack NFT warning. It is not: moving it behind a lazy guard leaves the warning unchanged, as does `join(process.cwd(), …)` — the shape the warning text itself recommends. Both experiments were **reverted rather than kept**, since neither buys anything and the lazy guard trades away a boot-time guarantee for nothing. The entry now records three negative results and points the next attempt at bisecting the route's other module-scope imports. A wrong hypothesis left in a backlog costs the next person the same hour.
- **Not done, and why:** converging the five property pickers onto `SearchableSelectPopover`. There is no zero-visual-change path — the pickers share one visual family (`text-sm`, `px-3 py-1.5`, `font-medium`-only selected state) that differs from the searchable popover's (`text-xs`, `px-2 py-1.5`, `rounded-md` rows, `bg-brand-subtle` selected), converging would drop `label-select`'s `✓`, and it would **add a search box to lists that have none**. That is a feature change needing browser QA and a design call, not a refactor. `label-select` would additionally need multi-select support the primitive doesn't have.

Full gate suite green on the pinned Node 24 (`yarn lint`, `yarn lint:tokens`, `yarn typecheck`, `yarn test` — 1751, `yarn build`, `docker build`).

Likewise the `Toggle` → `SettingToggleRow` swap in `settings/security` was already done on main, in a superset form, and was discarded wholesale.

Any colour literal carried across that boundary needs re-checking against `success` / `danger-subtle` / `primary-foreground` / `shadow-e1`, not just re-compiling.
- **`ProgressBar` deliberately always renders its fill div.** `project-detail-view` previously omitted the fill entirely while the server progress query was in flight; the shared component renders `width: 0%` instead. Visually identical, one less branch — but it means a test asserting "no fill child while loading" would need updating.

## Recently shipped (2026-08-04, i18n audit — the dictionary's silent failures)

- **A full sweep of the i18n layer: every locale key, every `t()` call site, and the locale round-trip.** Ten user-visible defects fixed, plus the guard that would have caught the worst of them. Full gate suite green (`yarn lint`, `yarn lint:tokens`, `yarn typecheck`, `yarn test` — 1718, `yarn build`).
- **The dictionary fails silently in both directions, which is why these shipped.** `translate()` returns the *key* on a miss and the `key` parameter is a bare `string`, so a key nobody defined renders its own dotted path into the UI — no throw, no type error. Two were live: `csv-export-button.tsx` asked for `issues.cycleNumber` (never defined), writing the literal text `issues.cycleNumber` into every exported CSV's Cycle column for un-named cycles; `create-project-modal.tsx` asked for `projects.status.label`, labelling the create-project status field `projects.status.label`. The CSV one now reuses the existing `cycles.defaultName` ("Cycle {number}") rather than adding a duplicate string.
- **The worst bug was a map keyed on the wrong vocabulary.** `activity-timeline.tsx`'s `FIELD_LABEL_KEYS` was keyed by *UI* field names while the server writes *column* names to `IssueActivity.field` — so `stateId` (every status change), `labelAdded`/`labelRemoved`, `parentId`, `startDate`, `trashed`, `commentResolved`/`commentUnresolved` all missed, and `getFieldLabel` returns the raw field when a key is absent. The activity feed read "Alice changed **stateId** from … to …" in *every* locale, English included, without ever reaching `t()`. Meanwhile the map's `status` and `labels` entries were unreachable — nothing ever emits those names. ## Recently shipped (2026-08-02, installable web app)

- **The app is now installable from Chrome's omnibox** (and every other Chromium browser, plus Safari's "Add to Dock"). Three pieces: a manifest route (`src/app/manifest.ts` → `/manifest.webmanifest`, localised and `APP_NAME`-aware, so Next injects the `<link rel="manifest">` itself), a committed icon set, and a service worker. **Verified in a real Chromium, not argued**: `Page.getAppManifest` reports zero manifest errors, `Page.getInstallabilityErrors` comes back **empty** against a `next start` build, the worker activates at root scope, and an offline navigation to a deep workspace URL renders the fallback page (back online, the real page returns). Full gate suite green after the rebase (`yarn lint`, `yarn typecheck`, `yarn test` — 1713, `yarn lint:tokens`, `yarn build`). See PATTERNS.md §81.
- **The service worker caches nothing but the offline page, deliberately.** It exists because Chrome wants a `fetch` handler and because a dead network should show something better than the browser's error screen — not to precache the app shell. Every HTML response here is rendered per user and per workspace (viewer's org, teams, role), so a cached copy is a staleness problem and, on a shared machine, a disclosure one; the offline story already lives a layer up in Dexie + `TransactionQueue`. Caching the shell safely needs a *user-independent* shell route, which doesn't exist — that's the work if it's ever revisited, not "add the HTML to the precache list". `/_next/static` is left alone too: content-hashed and already `immutable` for a year, so an SW cache in front of the HTTP cache buys nothing and adds a second unbounded copy.
- **Two properties of the fetch handler are the ones that would be incidents.** Only navigations are intercepted, so `/api/graphql`, `/api/sync/*`, uploads and the realtime endpoints reach the network untouched. And a server error is *not* "offline": `fetch` rejects only when the network is unreachable, so a 4xx/5xx passes straight through rather than being disguised as a connectivity problem.
- **The worker is executed by its own test.** It lives in `public/`, where Biome doesn't lint it, TypeScript doesn't see it and the build just copies it — and a bad one keeps running in real browsers after the deploy that fixed it. So `src/lib/pwa.test.ts` runs the real source in a stand-in worker scope (globals passed as parameters, so it can't reach Node's `fetch` by accident) and drives the handlers with synthetic events. Verified non-vacuous by neutering the navigation guard and watching six assertions fail.
- **Registration is production-only and dev actively unregisters.** A worker installed by a production build outlives its page and would go on intercepting navigations against the dev server on the same localhost origin — which also keeps it out of the e2e suite, since that runs against `next dev`.
- **The two colours that can't be tokens are guarded anyway.** `theme_color`/`background_color` and the `<meta name="theme-color">` pair are the only literal colours in the app: a manifest is JSON handed to the OS, and the meta tag is read before any stylesheet exists. `yarn lint:tokens` can't see them (it bans hex; these are `rgb()`), so `src/app/manifest.test.ts` resolves `--background` out of `globals.css` for both themes, converts oklch→sRGB and asserts the literals match — plus every icon's file existence and real pixel size, read from the PNG header.
- **Icons are generated, not hand-drawn** (`scripts/generate-pwa-icons.mjs`): headless Chromium screenshots a tile whose gradient is the same `oklch()` values as `globals.css` and whose glyph is set in the same vendored Instrument Sans, so the mark can't drift from the product. The maskable icon is a separate file from the `any` ones — maskable is full-bleed and cropped inside an 80% safe zone, so one icon declared as both purposes is wrong for one of them. Icon and splash screen use the default accent: they're baked into the launcher entry at install time and can't follow the user's chosen accent.
- **Not built, deliberately:** a custom in-app install button (`beforeinstallprompt`). Chrome's omnibox affordance already covers it, and a second entry point is UI worth adding only if install rates say so. Installation itself still needs HTTPS — localhost is the only exception.

- **A CI-only failure, and the reason it was CI-only.** The four navigation tests threw `Cannot read private member #state` on the runner while passing locally. The harness built its navigation request as `Object.create(realRequest, { mode: … })` — but an object whose *prototype* is a `Request` is not a `Request`, and every accessor on `Request.prototype` reads a private class field, which throws for any receiver that isn't a genuine instance. Node 22 tolerated it (undici kept that state off-instance); **Node 24, which `.node-version` pins and CI uses, does not**. The harness now wraps the request in a `Proxy` that overrides `mode` and forwards everything else through `Reflect.get` *without* a receiver, so the accessors keep seeing the instance they belong to. Worth knowing for the next agent: this sandbox's default `node` is 22, so `yarn test` here is not the runtime CI runs — install 24 (`nvm install 24`) before trusting a green local suite.

## Recently shipped (2026-08-02, cache-completeness stamp + the two verifications that were owed)

- **The three residuals left over from #112/#117**, all of which had been deferred as "needs infra this environment lacks". Two of the three turned out to be reachable here after all. Full gate suite green (`yarn lint`, `yarn typecheck`, `yarn lint:tokens`, `yarn test` — 1671, `yarn build`).
- **A warm cache can be *present* without being *complete*, and only presence was being checked.** `loadFromIndexedDB` returned true on the existence of a `lastSyncId`. A Dexie upgrade that *adds* a collection creates that table empty and carries the rest over — so the cursor survives, the cache looks usable, `start` takes the delta path, and the delta path only carries rows that *changed*. The new collection would never backfill and whatever reads it would render an empty state indefinitely. `fullBootstrap` now stamps `CACHED_COLLECTIONS` into `syncMetadata` **inside the same transaction as the rows it describes**, so the claim can't outlive a failed write, and `loadFromIndexedDB` refuses any cache whose stamp doesn't cover every required collection. Caches written before the stamp existed have none and are correctly refused once.
- **`CACHED_COLLECTIONS` lives in its own module** (`src/lib/db-collections.ts`), not `db.ts`, because `db.ts` constructs an `AppDatabase` at module scope — anything importing it drags IndexedDB in, including `sync-manager.test.ts`, which mocks `./db` wholesale and would have seen the constants as `undefined`.
- **A drift guard, not just a constant.** The stamp only means anything if it describes the real write set, so a test parses `sync-manager.ts` for the bootstrap transaction's `db.<name>.clear()` calls and asserts they are exactly `CACHED_COLLECTIONS`. Add a collection to bootstrap and forget the constant, and the stamp would claim a complete cache while the new table stayed empty on every client — the precise hole the mechanism exists to close, reintroduced silently. Verified non-vacuous by neutering the check and watching both refusal tests fail.
- **`favorites` is deliberately excluded**, and finding out why was worth the detour: the server's bootstrap payload doesn't carry favorites at all, `fullBootstrap` neither clears nor writes them, and the sidebar reads them straight from GraphQL using the store only as a refetch trigger. Listing it would have made every client re-bootstrap forever, since bootstrap could never satisfy the claim. `pendingTransactions` is excluded for a sharper reason — it is the offline queue, the one thing in the cache that exists nowhere else.
- **`db.issueActivities` is gone**, by deleting it from the in-place `.version(1)` block rather than bumping to `.version(2)`. A version generation only earns its keep once there is a real client whose data has to survive the change, and nothing is deployed — the same reasoning as the migration-consolidation policy for Prisma. The cost is that a dev browser keeps an orphaned object store until it clears the database, which is the identical trade the `bilinear` rename already made. The `TODO(pre-launch)` for real `.version(N)` + `.upgrade()` migrations stays, and now records why editing v1 is still correct today.
- **The index benchmark that was owed since the DB-hardening pass now exists** (`yarn db:verify:indexes`). All seven hot-path queries are index-served on a 100k-issue dataset, none seq-scans. **The data distribution mattered far more than the row count** — the first cut put every issue on one team and one assignee, which made the team partial index "fail" with a 31 ms sequential scan and the assignee compound index lose to the plain single-column one. Both were correct plans for a predicate matching every row. Spreading over 8 teams / 6 states / 20 users is what makes the number mean anything; that trap is written into the script header so the next person doesn't re-learn it.
- **The xid8 fence's never-skip property is now demonstrated rather than argued** (`yarn db:verify:fence`). Two real concurrent sessions: A begins and inserts without committing; B inserts and commits with a *higher* BIGSERIAL id; a delta read in that window must return neither row; A commits out of id order; the same cursor must then yield both, A first. The script also asserts the counterfactual on the same data — an id-ordered read *does* serve B, which is exactly how the pre-fence cursor would have advanced past A and lost it permanently. This cannot be a unit test: the property only exists while a real transaction holds a real xid open.
- **What the fence work still does not cover**, now stated precisely in DATABASE_SCHEMA §2.22 instead of a blanket "needs a staging soak": sustained concurrent write load, xid wraparound, and a long-running transaction holding `xmin` back far enough to stall delta for an entire org.

### Rebase notes

This branch was rebased twice while in flight, and adapted to what it landed on rather than merely made to compile.

- **First, onto the xid8 commit-order fence (#100) and multi-org accounts (#109).** The fence replaced the `(committedAt, id)` delta cursor with `(xactId, id)` and **dropped `sync_actions.committed_at` entirely**, so the retention work built on top of it needed redesigning, not just conflict resolution.
- **Retention is now split across two clocks, deliberately.** The sweep prunes by `created_at` (wall-clock policy, and the column has its own index), but the staleness *mark* records the highest `xact_id` deleted — because that is the space the delta cursor lives in. A timestamp mark can no longer be compared against a cursor at all. `Organization.syncActionsPrunedThroughXactId` is `Decimal(20,0)`, not `BigInt`: xid8 is unsigned 64-bit and would overflow a signed int8 at the top of its range — verified by round-tripping a 20-digit mark through the column.
- **Prune and mark are one statement.** A data-modifying CTE does `DELETE … RETURNING` → `MAX(xact_id)` per org → `UPDATE organizations`, so the mark-vs-delete ordering hazard is structurally impossible rather than merely handled. `GREATEST(COALESCE(existing, 0), …)` keeps the mark monotonic. Exercised against a real Postgres 17 — unit tests can only assert the shape of raw SQL — covering both the prune itself (stale rows deleted, fresh row surviving, mark set to a real xid) and the monotonicity guard (a later prune at a lower xid does not lower the mark).
- **The `'0-0'` bootstrap-cursor loop exists in xid8 space too.** `latestSettledCursor` returns `'0-0'` for an org with no settled rows, which reads as "infinitely far behind"; once that org has had anything pruned, delta answers `staleCursor` and sends the client back to bootstrap forever. It now anchors at the snapshot frontier — `xmin - 1`, since the cursor is exclusive and a row exactly at `xmin` belongs to a still-in-flight transaction.
- **`migrate diff` always reports one index as drift** (`sync_actions_organization_id_xact_id_id_idx`), because Prisma can't declare an index on an `Unsupported("xid8")` column. Verified this reproduces on pristine `main` by deploying main's migrations to a separate container, so it is inherent to the fence design rather than introduced here; DATABASE_SCHEMA.md's verification recipe now says so, and it is the *only* drift the recipe should report.
- **Second, onto the membership-sync hardening (#111) and the `bilinear` rename (#115).** Three things were taken from main rather than kept from this branch: `normalizeIssueRow` had landed there independently and byte-identically, so the shared helper is simply main's; main's `issues_team_id_state_id_active_idx` — chosen from a measured hot path — **supersedes and replaces the two speculative partial live-set indexes** this branch had added on `issues`, which were dropped; and the Dexie rename plus the eight tests #111/#113 had broken both come from main.
- **One overlap worth knowing:** main's bootstrap now `replaceAll`s each store individually (including `organizationMemberStore`), while this branch added `RootStore.clearEntityPools()` ahead of the same block. They compose — the clear runs first and every store is repopulated behind it — so the pass is redundant for the stores main enumerates and still load-bearing for the ones it doesn't.

## Recently shipped (2026-08-02, multi-org follow-ups: roster sync, leaving, cached org role)

- **The three things §78 deliberately deferred, built.** Each was deferred for a stated reason; each reason is addressed rather than waived. Full gate suite green (`yarn lint`, `yarn typecheck`, `yarn lint:tokens`, `yarn test` — 1396, `yarn build`).
- **The org roster is in the sync pipeline**, so `'D'`/`'U' OrganizationMember` SyncActions stop being inert. They were emitted for parity and no client had a case for them, which meant the settings page reconciled its own copy locally and a second admin's open tab kept listing someone who had been removed until they reloaded. Now carried the whole way: `getBootstrapData` ships `organizationMembers`, Dexie gains the table, `OrganizationMemberStore` holds it, and `applyActions` routes the live actions. **Deliberately a separate collection from `users`** — nothing ever deletes a `User` row, so after a removal the person is still in `userStore`, and membership presence is the only thing that distinguishes a current member from a departed one. `MembersSection` derives its roster, `canManage` and last-owner check from the store, which **deleted** its own query, its optimistic apply, and that apply's rollback branch (a rejected role change now simply never moves the store).
- **`organizationLeave`** — separate from `organizationMemberRemove`, which still refuses self-removal, because the two differ in who bears the consequence: removal is done *to* someone by an admin, leaving is done *by* you. Folding them together meant either dropping the self-guard (a mis-click on your own row ejects you) or giving "leave" an admin-only check it should not have. They share the write through one private `deleteMembership`, so leaving cascades team memberships in the same transaction and inherits the last-owner guard — an owner may leave only once another owner exists, since otherwise the workspace is stranded and, unlike a removal, there is no second party to notice. - **The session's org role is cached on `AuthContext`.** `extractAuthContext` already selects `role` on the membership row it must read for the validity check; `requireOrgRole` re-queried the same unique index at each of its ~25 call sites, per mutation, for a value the request already had. It is now `requireOrgRole(ctx, roles)` and **synchronous**. Two invariants make that safe and are asserted: `orgId` and `orgRole` are cleared in the same assignment (a role without an org is refused as defence in depth), and every call site runs before its resolver's first write, so nothing observes a role it changed itself.

## Recently shipped (2026-08-01, multiple organizations per user)
