# Project Guidelines

This file provides guidance to AI Agents when working with code in this repository.

## Project Overview

A Linear-style issue tracker built with Next.js 16 (App Router), Apollo Server GraphQL, Prisma 7, PostgreSQL, MobX, and real-time sync via WebSocket + Redis Pub/Sub. Offline-first with Dexie.js (IndexedDB) client cache.

### Recently shipped (2026-08-02, client/server contract gaps + schema/sync residuals)

- **Closed out every residual carried in this file plus the audit backlog.** Full gate suite green (`yarn lint`, `yarn lint:tokens`, `yarn typecheck`, `yarn test` — 1635, `yarn build`), and the DB half verified against a real Postgres 17 per the DATABASE_SCHEMA.md recipe: both migrations apply, `migrate diff --from-config-datasource --to-schema` reports **only** the one inherent xid8-index drift (see the rebase notes below) and nothing else, `yarn db:seed` runs green, and every custom object plus the new FKs/column are confirmed via `pg_indexes`/`pg_constraint`/`information_schema`. See PATTERNS.md §77.
- **The recurring-bug root cause is gone.** 72 SDL positions normalized: every entity-reference argument and input field is now `ID`/`ID!` rather than a `String!`/`ID!`/`String`/`ID` grab-bag across 24 `teamId` positions and six other id names. GraphQL compares the *declared* variable type against the argument type, so the inconsistency made `$teamId: String!` vs `teamId: ID!` a coin flip — the exact failure that started this whole line of work. Deliberately excluded: `lastSyncId` (opaque BIGSERIAL cursor, already uniform), `slugId`, `idpEntityId`. Only two client documents broke, and they were the duplicate pair — the same one-line fix needed twice, which is the argument for §77.1 in miniature.
- **`sync_actions` retention, done safely.** An hourly sweep prunes past `SYNC_ACTION_RETENTION_DAYS`, but a sweep alone silently loses data for a long-offline client. The sweep records `Organization.syncActionsPrunedThroughXactId`, and `getDeltaSyncActions` answers `staleCursor: true` for a cursor at or below it so the client re-bootstraps instead of carrying a permanently-incomplete pool. The check is against the recorded mark, **not** a computed `now - retention` horizon — a horizon can't tell "pruned" from "org is younger than the window", and would have forced a needless bootstrap on every client holding a legacy id-only cursor (which `parseCursor` maps to the zero cursor precisely so delta *can* catch it up).
- **Yjs blobs no longer ride SyncAction payloads.** Stripped in `recordSyncAction` — the one choke point all ~20 emitters and 7 row-producers pass through, including raw `prisma.issue.findUnique` calls in `automation.service.ts` and `ws/index.ts` that a per-service fix would have missed. Verified empirically that a `Bytes` column in a `Json` argument does **not** throw: Prisma base64-encodes it, so this was silently shipping ~1.33× the blob to every client in the org and into their IndexedDB.
- **Three missing FKs**, each with delete semantics chosen from what null *means*: `File.uploaderId → User` SetNull, `Webhook.teamId → Team` Cascade (null means org-wide, so SetNull would silently broaden a team webhook), `SlackIntegration.defaultTeamId → Team` SetNull. All three confirmed against Postgres via `pg_constraint.confdeltype`.
- **Bootstrap's ProjectUpdate cap** was org-wide (`take: 500`) while shipping every issue uncapped — now a nested per-project `take` of 50 under a global ceiling of 1000, with an `id` tiebreak so *which* rows land is deterministic across bootstraps.
- **Dead code and name collisions:** the `IssueActivity` sync case was dead on both ends (no server emitter, nothing reads the table) and is removed; `CREATE_MUTATION` and `CYCLE_VELOCITY_QUERY` each named two different documents in two files — note `CYCLE_VELOCITY_QUERY` turned out to be genuinely *different* documents (root `cycleVelocity` vs `analyticsCycleVelocityTrend`), so they were renamed rather than merged; the duplicated issue-templates document is consolidated onto the shared export.
- **Post-review hardening.** A code review caught that the retention sweep marked *every* org, not just those whose rows were pruned — combined with bootstrap returning a zero cursor for an org with no surviving actions, that produced a permanent delta → staleCursor → bootstrap loop re-downloading the workspace on every reconnect. Both halves fixed. Same review found an e2e document still declaring `$teamId: String!` — the guard only scanned `src/`, so it now scans `tests/` too, bringing 12 further documents under validation.
- **§77.1 is now actually enforced.** PATTERNS claimed the document-validation suite guarded the ID convention. It did not — that suite checks documents *against* the SDL, so a new `teamId: String!` field paired with a matching document passes. There is now a schema assertion walking every input field and argument; verified non-vacuous by injecting a violation. It ignores output fields on purpose (variables are never compared against those).
- **Fetch-on-mount consolidated onto `useRetryableFetch`** across 15 components — the error-handling sweep had hand-rolled the same `reloadKey`/`cancelled`-flag state machine fifteen times, ~160 net lines removed. Documented as the required pattern in PATTERNS.md §77.6 so the next sweep doesn't re-derive it.
- **`Project.progress`/`scope` columns deleted.** Nothing ever wrote them — the server computes progress from the issue set on read — so every reader silently rendered 0%. Removing the columns turned each stale read into a compile error, which surfaced one nobody had found: `roadmap/[slug]/page.tsx` had its *own* `prisma.project.findMany` reading the raw column, separate from the roadmap service already fixed. Also caught a dead `progress: true` select in `initiative.service.getProjects()` whose only consumer uses `link.id`. Both fields survive as **computed GraphQL fields** (`Project.progress`/`scope`, resolved through the DataLoader) — only the columns went, which is what `IMPLEMENTATION_PLAN.md` always described (`[x] … computed from completed vs total issues (project.service.ts#getProgress)`).
- **`Cycle` carries the same six dead columns, and they are *not* removed here.** An earlier revision of this entry claimed cycles' `progress`/`scope` "are written" — that is **wrong**, and worth recording because it was asserted without checking. The only two `prisma.cycle.update` sites write name/description/dates and `archivedAt`; neither `tx.cycle.create` site writes progress or scope; nothing reads them; and `Cycle`'s four `*History` JSONB columns appear only in a test fixture. `CycleService.getProgress` computes from the issue set exactly like the project path. `Initiative.progress` is the genuine cached rollup — it *is* written (`initiative.service.ts`) and read back by the recursive rollup, which is the case the wrong claim was probably confused with. Cycle's six are left for a follow-up: no reader renders a stale value from them, so unlike `Project` there is no user-visible bug forcing the change.
- **Progress now resolves through a `projectProgress` DataLoader** backed by `getProgressBatch` (two `groupBy` queries for any number of projects). The previous per-request memo still issued two `issue.count` queries *per project*, so a 20-project list cost 40 round-trips. That's what makes fetching progress for a whole list viable, which in turn let the project list/detail views stop computing it from `issueStore` — a guest's pool is scoped to their own issues, so one owned issue in a 50-issue project rendered 100%.

#### Rebase notes

This branch was rebased twice while in flight, and adapted to what it landed on rather than merely made to compile.

- **First, onto the xid8 commit-order fence (#100) and multi-org accounts (#109).** The fence replaced the `(committedAt, id)` delta cursor with `(xactId, id)` and **dropped `sync_actions.committed_at` entirely**, so the retention work built on top of it needed redesigning, not just conflict resolution.
- **Retention is now split across two clocks, deliberately.** The sweep prunes by `created_at` (wall-clock policy, and the column has its own index), but the staleness *mark* records the highest `xact_id` deleted — because that is the space the delta cursor lives in. A timestamp mark can no longer be compared against a cursor at all. `Organization.syncActionsPrunedThroughXactId` is `Decimal(20,0)`, not `BigInt`: xid8 is unsigned 64-bit and would overflow a signed int8 at the top of its range — verified by round-tripping a 20-digit mark through the column.
- **Prune and mark are one statement.** A data-modifying CTE does `DELETE … RETURNING` → `MAX(xact_id)` per org → `UPDATE organizations`, so the mark-vs-delete ordering hazard is structurally impossible rather than merely handled. `GREATEST(COALESCE(existing, 0), …)` keeps the mark monotonic. Exercised against a real Postgres 17 — unit tests can only assert the shape of raw SQL — covering both the prune itself (stale rows deleted, fresh row surviving, mark set to a real xid) and the monotonicity guard (a later prune at a lower xid does not lower the mark).
- **The `'0-0'` bootstrap-cursor loop exists in xid8 space too.** `latestSettledCursor` returns `'0-0'` for an org with no settled rows, which reads as "infinitely far behind"; once that org has had anything pruned, delta answers `staleCursor` and sends the client back to bootstrap forever. It now anchors at the snapshot frontier — `xmin - 1`, since the cursor is exclusive and a row exactly at `xmin` belongs to a still-in-flight transaction.
- **`migrate diff` always reports one index as drift** (`sync_actions_organization_id_xact_id_id_idx`), because Prisma can't declare an index on an `Unsupported("xid8")` column. Verified this reproduces on pristine `main` by deploying main's migrations to a separate container, so it is inherent to the fence design rather than introduced here; DATABASE_SCHEMA.md's verification recipe now says so, and it is the *only* drift the recipe should report.
- **Second, onto the membership-sync hardening (#111) and the `bilinear` rename (#115).** Three things were taken from main rather than kept from this branch: `normalizeIssueRow` had landed there independently and byte-identically, so the shared helper is simply main's; main's `issues_team_id_state_id_active_idx` — chosen from a measured hot path — **supersedes and replaces the two speculative partial live-set indexes** this branch had added on `issues`, which were dropped; and the Dexie rename plus the eight tests #111/#113 had broken both come from main.
- **One overlap worth knowing:** main's bootstrap now `replaceAll`s each store individually (including `organizationMemberStore`), while this branch added `RootStore.clearEntityPools()` ahead of the same block. They compose — the clear runs first and every store is repopulated behind it — so the pass is redundant for the stores main enumerates and still load-bearing for the ones it doesn't.

- **Known residuals, deliberately:** live notification delivery still needs a per-user WS channel (org-wide SyncActions can't carry private notifications); the xid8 fence still wants a staging soak against a real workload; and `db.issueActivities` is now provably unused but left in place — dropping it needs the Dexie version bump #115's TODO already tracks. Browser QA and an end-to-end `docker build` remain outside what this environment can reach.


### Recently shipped (2026-08-02, membership-sync hardening)

- **Follow-up to the roster/leave/`orgRole` work in #108**, which shipped those three features but left the write side and a handful of edges unguarded. Rebased onto #115, which independently fixed the eight tests #108/#113 had broken between them and renamed the Dexie database — both of which this branch had also carried, and both now taken from main. - **Four of the six membership writers emitted nothing.** Only the two GraphQL mutations broadcast; invitation acceptance, SCIM provisioning, SCIM re-activation and SAML JIT provisioning wrote `organization_members` directly. Survivable when the members UI refetched on mount — it doesn't anymore, and a warm Dexie cache takes the delta path, so an IdP deprovisioning someone left them in every admin's roster *permanently*, with controls that returned `NOT_FOUND`. All six now share `src/server/lib/membership-sync.ts`.
- **A membership `'I'` is inert on its own.** Bootstrap scopes `users` to current members, so a client already running when someone joins has no `UserStore` row for them, and the members list is the intersection of the two pools. `announceJoin` ships the `User` row (under `USER_SYNC_OMIT`, now one constant shared with the bootstrap query) ahead of the membership. `broadcastMembership` is typed `Exclude<SyncActionType, 'I'>` so a join cannot skip it.
- **Leaving cleared nothing from the request context.** GraphQL runs root mutation fields serially against one context, so `organizationLeave` followed by `organizationInviteCreate` in the same document authorized on the membership the first field had just deleted — mailing an admin invitation into a workspace the caller provably no longer belonged to. `clearOrgSession(ctx)` nulls `orgId` and `orgRole` together; the rest of the document fails closed with `UNAUTHENTICATED`.
- **SCIM could deprovision but never undo it.** `PUT`/`PATCH` resolved the target through the org-scoped membership row and 404'd before reaching the `active: true` branch — on the very row deactivation had deleted. Both now parse the body first and let a re-activation through to a new `reactivateUser`, which resolves the user globally (no new privilege: `POST /Users` already adds arbitrary addresses to the org). `DELETE` lost its pre-check too, so `deactivateUser`'s documented idempotency is reachable from the endpoint IdPs retry most. PUT and PATCH also stopped duplicating ~35 lines.
- **Bootstrap `replaceAll`s the roster instead of merging**, and its write phase runs on the `applyLock`. `fullBootstrap` is also the delta-failure fallback, running *after* a warm cache filled the pool and with the socket live — merging kept removed members, and an unlocked authoritative write could erase an action landing between the clear and the repopulate. The fallback also gained the `scheduleFollowUpDelta()` the cold-start path already had.
- **A finding recorded rather than coded.** This branch originally replaced the `issue-tracker-vN` rename with an in-place `.version(2)` block, because the rename orphans `pendingTransactions` — queued offline writes, the one thing in that database that exists nowhere else. #115 reached the same conclusion and resolved it differently (rename once to `bilinear`, keep editing `.version(1)` pre-launch, commit to a fixed name plus `.version(N)` before deployment), so that half is dropped. What survives is the consequence #115's TODO does not yet cover, now written into it: a Dexie upgrade creates a newly *added* table empty, `loadFromIndexedDB` still reports a usable cache, and delta carries only changed rows — so an untouched collection never backfills. The `.version(N)` work will need a collection-set stamp in `syncMetadata` alongside it.
- **Leaving now confirms before discarding queued offline writes** (the switch already did, and leaving is worse — those edits belong to a workspace the user can no longer reach), and a cookie-install failure *after* the server-side leave reloads through `/` instead of reporting a failure that did not happen.
- **`Query.organizationMembers`, `OrganizationMemberEntry` and `OrganizationService.findMembers` are deleted** — the store-backed roster left them with no caller.
- **The raw-SyncAction test mock is shared.** `recordSyncAction` writes through `INSERT … RETURNING` for the DB-assigned `xact_id`, so `prisma.syncAction.create` is off the path; the stub was hand-rolled in `github.service.test.ts` and now lives in `src/test/sync-action-mock.ts` for both it and the SAML tests.

### Recently shipped (2026-08-02, delta-sync commit-order fence + per-org caps admin UI)

- **Rebased onto the 2026-08-01 multi-org / migration-consolidation / client-server-contract work below**, and reconciled with it (not merely made to compile): the delta-sync rewrite composes with #107's `getBootstrapData` hardening (the sensitive-column `omit`s on the org/user reads, the `projectUpdate` `archivedAt` filter) and with the `Organization`/`Notification`/Issue-shape `applyActions` handlers in `sync-manager`; the settings caps view uses the new `gqlQuery` helper (§76); the migration additions fold into the regenerated baseline per the migration-consolidation policy below.
- **Delta-sync commit-ordered reads via xid8 / snapshot-xmin fencing** — closes the highest-value correctness residual (the delta watermark was still an app-server-clock heuristic). `sync_actions.committed_at` (`statement_timestamp()` + a 500ms wall-clock safety window) is replaced by an `xact_id xid8 NOT NULL DEFAULT pg_current_xact_id()` column. Delta reads (`SyncService.getDeltaSyncActions`/`getLastSyncId`/`getBootstrapData`) now use raw SQL that orders by `(xact_id, id)` and reads only rows with `xact_id < pg_snapshot_xmin(pg_current_snapshot())` — rows whose transaction has SETTLED and below which no transaction is still in flight. This is provably never-skip: a transaction that inserts its SyncAction early but commits arbitrarily later can no longer be missed (its xid keeps its rows fenced until it actually commits), and there is no app-vs-DB clock to reconcile (the `SELECT now()` round-trip is gone). Cursor format is now `<xactId>-<id>`; a stale `<committedAtMicros>-<id>` cursor from before this change self-heals (its huge first component is reset to the zero cursor for a full re-read — see `MAX_PLAUSIBLE_XACT_ID`) rather than wedging delta. `SerializedSyncAction`/`sync-manager` carry `xactId` instead of `committedAt`; `recordSyncAction` inserts via raw `INSERT … RETURNING` to get the DB-assigned `xact_id` back in one round-trip (the Prisma query builder can't select an `Unsupported("xid8")` column). The bootstrap cursor is read BEFORE the entity fan-out so it can only lag, never lead (a transaction committing mid-bootstrap stays above the cursor and is re-read by the first delta). `COMMIT_WATERMARK_LAG_MS` is retained purely as the client-side post-connect settle delay. The `committed_at` column/index/trigger are removed. **Needs a real-Postgres staging soak**; the `xact_id xid8 DEFAULT pg_current_xact_id()` column is Prisma-expressible (`Unsupported` + `dbgenerated`) so it's folded into the regenerated `00000000000000_init` baseline per the migration-consolidation policy below, and only its `(organization_id, xact_id, id)` covering index lives in the custom migration (Prisma can't `@@index` an `Unsupported` field). Run the DATABASE_SCHEMA.md verification recipe against a throwaway Postgres before deploy. See DATABASE_SCHEMA.md §2.22.

### Recently shipped (2026-08-01, UI/UX revamp — L1–L4)

- **Full UI/UX revamp in four bottom-up layers**, each independently shippable. Direction agreed up front from a visual pitch: **expressive/gradient-accented**, under one governing rule — in an issue tracker most of the spectrum is already spoken for by data (red/orange/yellow = priority, green = completed, slate = backlog), so the gradient lives entirely in the **chrome** (selection rails, focus glow, elevation, one primary action) and never touches the data layer. That constraint is also why all three accents sit in the cool violet–azure arc: it is the only band that can't be misread as status. Full gate suite green at every layer (`yarn lint`, `yarn typecheck`, `yarn lint:tokens`, `yarn test` — 1118, `yarn build`).
- **L1 — foundation.** `next/font` was used *zero* times, so the app rendered in whatever the OS shipped; **Instrument Sans** (UI) + **Geist Mono** (identifiers, counts, timestamps) are now vendored as latin variable subsets under `src/app/fonts` and loaded via `next/font/local`, so the build never depends on a font CDN (both OFL, licences vendored). Every neutral is now computed in oklch from `--accent-h`, the active accent's own hue — they were `oklch(x 0 0)`, literally zero chroma, against an accent at 0.23, which is what made the chassis and the accent read as two unrelated systems. `--brand` is unified into `--primary`/`--ring`, closing the split where primary buttons and focus rings were neutral while links and badges were indigo. **`--accent` no longer equals `--muted`** — they were byte-identical, which is what made `bg-muted hover:bg-accent` render as no hover at all, a bug class this codebase had been patching call-site by call-site.
- **Selectable accent.** Aurora / Ion / Ultraviolet, chosen from the sidebar footer (cycling swatch), workspace settings (full picker) and the command palette. Persisted in the `accent` cookie and stamped on `<html>` during SSR, so there's no flash and no `mounted` guard is needed — this mirrors the locale preference (`src/lib/accent.ts`, `accent-server.ts`, `providers/accent-provider.tsx`), **not** `next-themes`. `User.accent` persists the choice to the account so it follows across devices, but it is read in exactly **one** place — the session route, which seeds the cookie at login. Unlike locale (which transactional emails need server-side), the accent has no other server-side consumer, and the root layout must never query for it: it resolves the accent from the cookie on every request. Each accent declares only `--brand` and `--brand-2`; every other brand role derives via `color-mix`, so **adding a fourth accent is one registry entry plus a four-line CSS block**.

Every row is now its own grid with an identical template and a reserved dot slot; six tests guard "exactly one track per rendered cell", since a template that drifts from its cells fails silently. The sidebar rendered **five always-expanded sub-links per team** (25+ nav rows at four teams) — exactly one team is now expanded, defaulting to the route's team or the first team. Every remaining raw Tailwind shadow moved onto the three-step elevation scale (0 left), and the four issue-list pages render `IssueListSkeleton` instead of a centred "Loading…" string.

### Recently shipped (2026-08-02, multi-org follow-ups: roster sync, leaving, cached org role)

- **The three things §78 deliberately deferred, built.** Each was deferred for a stated reason; each reason is addressed rather than waived. Full gate suite green (`yarn lint`, `yarn typecheck`, `yarn lint:tokens`, `yarn test` — 1396, `yarn build`).
- **The org roster is in the sync pipeline**, so `'D'`/`'U' OrganizationMember` SyncActions stop being inert. They were emitted for parity and no client had a case for them, which meant the settings page reconciled its own copy locally and a second admin's open tab kept listing someone who had been removed until they reloaded. Now carried the whole way: `getBootstrapData` ships `organizationMembers`, Dexie gains the table, `OrganizationMemberStore` holds it, and `applyActions` routes the live actions. **Deliberately a separate collection from `users`** — nothing ever deletes a `User` row, so after a removal the person is still in `userStore`, and membership presence is the only thing that distinguishes a current member from a departed one. `MembersSection` derives its roster, `canManage` and last-owner check from the store, which **deleted** its own query, its optimistic apply, and that apply's rollback branch (a rejected role change now simply never moves the store).
- **`organizationLeave`** — separate from `organizationMemberRemove`, which still refuses self-removal, because the two differ in who bears the consequence: removal is done *to* someone by an admin, leaving is done *by* you. Folding them together meant either dropping the self-guard (a mis-click on your own row ejects you) or giving "leave" an admin-only check it should not have. They share the write through one private `deleteMembership`, so leaving cascades team memberships in the same transaction and inherits the last-owner guard — an owner may leave only once another owner exists, since otherwise the workspace is stranded and, unlike a removal, there is no second party to notice. Returns a **`LeaveOrganizationPayload`, not `EnterOrganizationPayload`**: that type's `organization` is non-null because you always land somewhere, whereas leaving your last workspace legitimately lands you nowhere (an org-less session still authenticates for `viewerOrganizations` and workspace creation). The destination is resolved *after* the delete through the same usable-org filter login uses, so it can neither pick the org just left nor land on a suspended one.
- **The session's org role is cached on `AuthContext`.** `extractAuthContext` already selects `role` on the membership row it must read for the validity check; `requireOrgRole` re-queried the same unique index at each of its ~25 call sites, per mutation, for a value the request already had. It is now `requireOrgRole(ctx, roles)` and **synchronous**. Two invariants make that safe and are asserted: `orgId` and `orgRole` are cleared in the same assignment (a role without an org is refused as defence in depth), and every call site runs before its resolver's first write, so nothing observes a role it changed itself.

### Recently shipped (2026-08-01, multiple organizations per user)

## Architecture

### Request Flow

```
Client (MobX stores) → GraphQL mutation via fetch (no Apollo Client)
  → /api/graphql (Apollo Server) → Resolver (auth + delegation) → Service (business logic) → Prisma → PostgreSQL
  → SyncAction created → Redis Pub/Sub → WebSocket server → all org clients
```

### Key Boundaries

- **`src/server/`** — backend only, never imported by client code. Contains GraphQL resolvers, services, middleware, and lib singletons.
- **`src/stores/`** — MobX observable entity pools. Components read from stores, not GraphQL queries.
- **`src/lib/`** — client-side utilities (sync-manager, transaction-queue, ws-client, Dexie DB).
- **`src/components/`** — React components, feature-grouped. `ui/` has shadcn/ui primitives.

### Data Flow (Client)

1. **Bootstrap:** `/api/sync/bootstrap` → IndexedDB (Dexie) → MobX stores
2. **Writes:** Optimistic MobX update → `TransactionQueue` enqueues GraphQL mutation → rollback on error
3. **Real-time:** WebSocket receives SyncActions → MobX stores updated → components re-render via `observer()`
4. **Delta sync:** `/api/sync/delta` catches up missed changes via `lastSyncId`

### Resolver → Service Pattern

Resolvers are thin: `requireAuth(ctx)` → `ctx.services.<domain>.method()` → return result with `lastSyncId`. All business logic lives in services. Services return plain objects, never GraphQL types. Error classes are internal to each service; resolvers catch and remap to `GraphQLError` with `extensions.code`.

### Prisma 7 Split Config

- **CLI** (`migrate`, `generate`): uses `prisma.config.ts` with `defineConfig({ datasource: { url } })`
- **Runtime**: uses `@prisma/adapter-pg` in `src/server/lib/prisma.ts`
- **Generated client**: `src/generated/prisma/` (gitignored — run `yarn db:generate` after checkout or schema changes)

## Key Conventions

### Database

- UUID PKs, soft delete via `archivedAt`, audit timestamps on all models
- snake_case DB columns (`@map`), timezone-aware datetimes (`@db.Timestamptz`)

### GraphQL

- Error discriminator: `extensions.code` (UNAUTHENTICATED, NOT_FOUND, INVALID_CODE, INVALID_TOKEN, FORBIDDEN, RATELIMITED, BAD_USER_INPUT)
- Mutations return `{ success, <entity>, lastSyncId }` — lastSyncId is a string (BIGSERIAL)
- SyncAction must be created for every mutation: `ctx.services.sync.createSyncAction(orgId, action, model, id, data)`

### MobX Stores

- Wrap components with `observer()` from `mobx-react-lite`
- Use `useStore()` hook (from StoreProvider context) to access RootStore — never import `getRootStore()` directly. No Redux/Zustand/React Query/SWR; use `useState` for ephemeral local UI state only.
- Use `store.pool.size` as dependency in `useMemo`, not the Map itself
- `TransactionQueue` instances share a singleton in-memory FIFO backed by an IndexedDB `pendingTransactions` table. `new TransactionQueue()` per component mount with `useMemo(() => new TransactionQueue(), [])` is still the convention — every instance enqueues into the shared queue. Pending transactions survive a page reload, scoped to the session that enqueued them (`orgId`/`userId` from the JWT). `SyncProvider` calls `TransactionQueue.setActiveSession(...)` then `TransactionQueue.hydrate(session)` once at app boot; rows from other sessions are deleted, not replayed.

### Auth

- Magic link email with 6-digit codes. Hash before store (`crypto.createHash('sha256')`). CSPRNG only (`crypto.randomInt`).
- JWT via `jose` (edge-compatible). Access tokens 24h, refresh tokens 30d in httpOnly cookies.
- `requireAuth(ctx)` uses TypeScript `asserts` narrowing.
- E2E test bypass: `NODE_ENV=test` + `TEST_AUTH_CODE=000000`

### Frontend

- TailwindCSS v4 + shadcn/ui only — no CSS Modules, no styled-components. Dark mode via `next-themes` (class-based); accent colour via the `accent` cookie + `data-accent` on `<html>` (see `src/lib/accent.ts`).
- **No raw colours at all.** `yarn lint:tokens` bans every shade-numbered Tailwind palette hue (`red-500`, `zinc-700`, `blue-400`, …) and every hex literal across `src/components`, `src/app`, `src/lib` and `src/hooks`, at a literal-zero baseline. Use the token families: surfaces (`bg-background`/`bg-card`/`bg-muted`/`bg-accent` for hover/`bg-surface-raised`/`bg-surface-sunken`), ink (`text-foreground`/`-secondary`/`text-muted-foreground`/`text-foreground-faint`), brand (`bg-brand`, `bg-brand-subtle`, `text-brand-subtle-foreground`, `border-brand-border`), status (`danger`/`success`/`warning`/`info`/`merged`, each with `-subtle` and `-subtle-foreground`), and elevation (`shadow-e1` rows, `shadow-e2` popovers, `shadow-e3` modals). A fixed palette that genuinely can't be a token (priority swatches, cursor colours, accent swatches) lives in `globals.css` and is referenced from `.ts` as a `var()` string, never inlined.
- **Brand roles follow the user's accent; status roles never do.** Status encodes data — "this failed" must mean the same thing under every accent. Tests in `src/lib/accent.test.ts` enforce both halves.
- Typography: `--font-sans` is Instrument Sans, `--font-mono` is Geist Mono, both vendored under `src/app/fonts` and loaded with `next/font/local` (never `next/font/google` — the build must not depend on a font CDN). Identifiers, counts, estimates and timestamps go in `font-mono tabular-nums`.
- Use `cn()` from `@/lib/utils` (clsx + tailwind-merge) for all class merging — never template-literal concatenation.
- Component files live in `src/components/<feature>/` — feature-grouped, kebab-case filenames. Interactive components are `'use client'`; pages and layouts are server components.
- Large client-only widgets use `dynamic(..., { ssr: false })` with a `.lazy.tsx` suffix (e.g. `tiptap-editor.lazy.tsx`, `issue-detail-panel.lazy.tsx`).
- Toast notifications: use `@/lib/toast` wrapper, never import sonner directly. It exposes `error/info/success/warning` plus `undo(message, label, onUndo)`, `loading`, `promise`, and `dismiss(id)`. `TransactionQueue` permanent failures with no per-call `onError` fall through to a default toast registered by `SyncProvider` — never rely on that as the primary UX for a known failure path.
- Logging: use `logger`/`childLogger` from `@/server/lib/logger` (pino). No `console.log` in server code.
- UI primitives in `src/components/ui/`: `Button` (CVA), `Badge` (CVA, variants: `pill`/`solid`), `UserAvatar`, `Select`, `Skeleton`, `SelectPopover`, `SearchableSelectPopover` (generic searchable dropdown — see `CycleSelect`/`ProjectSelect` for usage), `ModalDialog` (native `showModal()` — real focus trap; Escape arrives as the `cancel` event), `Input`, `Textarea`, `Switch`, `PageHeader`/`Toolbar` (the single page-chrome header + its control strip — never hand-roll a page header), `EmptyState`. Extend here, not inline — don't hand-roll form fields, toggles, page headers or empty states.
- `/design` renders the whole token layer and every primitive across all three accents and both themes. Open it when changing anything in `ui/` or `globals.css`; this repo's CI has no visual regression suite.
- Full design-system reference — the two colour families and why status never follows the accent, the two-values-per-accent derivation, the specificity trap, and the primitive inventory — is **PATTERNS.md §79**.
- Shared sub-components in `src/components/shared/`: `UpdateFormFields`, `DeleteUpdateButton`, `ConfirmDialog` (destructive confirmations — prefer over `window.confirm`). Add cross-feature building blocks here.
- Escape contract: whichever surface consumes an Escape must claim it (`preventDefault` + `stopPropagation` — `useOutsideClick` does this for popovers, capture-phase). Window-level Escape listeners on parent surfaces must ignore handled events (`if (e.defaultPrevented) return`). One Escape closes exactly one surface.
- Issue mutations from components: use `useIssueCreate(team, states)` and `useIssueUpdate()` from `src/hooks/` — they own the optimistic apply, TransactionQueue enqueue, rollback, and failure toast. Map store models for issue components with `toIssueUsers`/`toIssueLabels` from `@/lib/issue-mappers`; don't hand-roll the mapping.
- Issue creation UI: there is exactly one create modal — `GlobalCreateIssueModal`, mounted in `WorkspaceClient` and driven by `uiStore.openCreateIssueModal()`. Open it from buttons/shortcuts/palette actions via the store; never mount a second `CreateIssueModal`.
- Dropdown/popover state: use `usePopover({ open?, forceOpen?, onClose?, closeOnEscape? })` from `@/hooks/use-popover` — returns `{ open, setOpen, ref }`. `open` is fully controlled (parent owns show/hide); `forceOpen` is a one-shot uncontrolled open. For outside-click only (no popover state), use `useOutsideClick` from `@/hooks/use-outside-click` directly — it also takes an optional `closeOnEscape` param.

### Testing

- Unit tests (Vitest): mock Prisma via `createMockPrisma()`, mock context via `createMockContext()`. Fixtures in `src/test/fixtures.ts`. If the subject emits a SyncAction, stub the write with `mockSyncActionInserts(prisma)` and assert with `readSyncActionInserts(prisma)` (`src/test/sync-action-mock.ts`) — `recordSyncAction` goes through a raw `INSERT … RETURNING`, not `prisma.syncAction.create`. Role-gated resolvers read `ctx.orgRole`, so express "caller lacks the role" there, not via a prisma mock.
- E2E tests (Playwright): `tests/e2e/`. Use `loginAs(page, email)` helper. Both dev server + WS server must be running.
- MockSyncService returns `{ id: BigInt(1) }` — assert `lastSyncId === '1'` (string).
